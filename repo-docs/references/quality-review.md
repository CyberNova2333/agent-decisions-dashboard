# 阅读质量审计

本页用于检验本指南是否向新读者传达了准确、可执行且不越界的心智模型，并显式列出剩余未覆盖风险。

## 读者模拟

| 检查问题 | 从指南得到的答案 |
| --- | --- |
| 主路径是什么 | 从回环 HTTP 读取版本、携带固定 `request_id` 与 `expected_version` 保存议题，经过锁、往返校验与分阶段落盘后，通过只读钩子分别核对台账与 Git 状态 |
| 核心难点是什么 | 写操作跨越 Markdown、SQLite、摘要 JSON 与 Git 四处状态，响应超时后盲目重读版本重发会造成重复讨论或版本冲突 |
| 阶段如何衔接 | 读取状态与版本 → 持久化保存原始请求载荷 → 锁内验重/CAS → 写入 Markdown/SQLite/快照 → 导出摘要并可选 Git 提交 → `after-write` 校验回执 |
| 边界与失败条件在哪 | 仅限单机回环、单进程管理单目录；`accepted`/`verified` 标签与 `agent-question` 选择均不构成执行授权或真实测试通过证明 |
| 如何独立验证理解 | 使用仓库内隔离临时测试目录执行 `unittest discover tests` 与 `node --test tests/*.test.js`，并用 `--check-consistency` 对照台账健康度 |
| 修改代码从哪里入手 | 按[代码地图](../code-map.md)和两篇模块文档定位 `core/` 对应服务/存储类、`web/` 渲染/协议模块及对应测试文件 |

## 可证伪性与后续问题

证伪检查：如果测试中同 ID 变更请求体可以绕过 `409 idempotency_conflict`、旧版本可覆写当前 Markdown，或者删除后同名重建版本回到 `1` 导致旧快照混用，说明核心保护机制已回归失效，本指南叙述不再成立。

读者下一问：如何为自定义项目接入工作台并在生产数据损坏前建立自动巡检？可先阅读根目录文档站 Stage 1「起步与配置部署」配置 `topic_scope` 与 `--config`，并定期调用 `POST /api/backup` 与 `--check-consistency`。

## 剩余风险

- 本指南重点阐明主服务后端、状态模型与前端核心协议，未展开 `DESIGN.md` 中的所有 CSS 质感样式变体；
- 独立文档站构建与结构校验不能替代真实浏览器下的完整 UI 操作回归或 Windows 本地脚本启动验证；
- `decisions/*.md` 被外部进程直接修改或与活跃服务并发写入时仍需人工对账后再重建索引，不存在跨进程自动合并保证。
